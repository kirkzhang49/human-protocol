# Implementation Patterns

Use this when a request requires code changes, not just level config edits.

## Reusable Mechanic Checklist

For a new config capability, wire every layer:

1. Schema: update `games/human-protocol/src/game/config/schema/levelConfig.ts`.
2. Level samples: add or update official configs in `src/game/config/levels` and/or smoke configs in `src/game/config/smoke`.
3. Runtime state: extend `MapProgressState` or nearby progress structures in `src/game/core/GameWorld.ts` only when state must persist through play.
4. Runtime behavior: update lookup methods, activation methods, `runConfiguredAction`, puzzle completion, objective requirements, and trigger handling.
5. Interaction handling: ensure the `InteractionSystem` and UI prompts can reach the new action without level-specific branches.
6. Rendering: update `MapGeometryRenderer`, `AssetResolver`, HUD/modal UI, or 3D renderer only when the player needs a visible affordance.
7. Validation: update `ConfigValidator` reference sets, duplicate checks, path checks, `validateRuntimeEventAction`, and graph simulation.
8. QA: update `scripts/real-playthrough-qa.mjs`, `scripts/smoke-campaign.mjs`, or add a smoke config that proves the chain can be completed.
9. Localization: official player-facing strings need Chinese and English coverage through existing localization/config patterns.

If any layer is missing, the system is probably fragile even if the app builds.

## Runtime Pattern

`GameWorld` should answer generic questions by ID:

- find article/quiz/switch/big screen by `interactionId` or `id`
- collect key item by ID
- complete objective by ID
- open/close/lock/unlock door by ID
- start wave by ID
- set screen/switch/environment state by ID

Runtime methods should not know that "level 04 body screen opens the theater" or "level 05 quiz starts the boss"; those are config action chains.

## Validator Pattern

When a config field references another entity, add a validator check. Typical reference sets include rooms, doors, interactions, key items, puzzles, waves, objectives, choices, articles, quizzes, switches, big screens, and environment states.

Graph simulation does not need to be a perfect puzzle solver, but it must catch:

- missing IDs
- unreachable exit rooms
- critical doors that never open
- keys behind their own only lock
- puzzle success actions that reference missing doors/waves/objectives
- quiz/switch/screen actions that block or unlock progression
- mobile enemy counts that exceed the current budget

## Formula Locks

Formula locks should use the existing safe arithmetic path:

- allow only digits, spaces, `+`, `-`, `*`, `/`, and parentheses
- do not use JavaScript `eval`
- support `answer`, `display`, `padLength`, and `resultMode`
- keep displayed clue separate from accepted answer when the design needs multiple digits from multiple rooms

## Config-Pack Direction

Design new systems as if they will later be generated by a local LLM:

- make IDs explicit and stable
- keep dependencies in data, not code branches
- emit validation errors that a generator could fix
- keep official levels as examples of valid generated configs
- avoid assets that require one-off code to appear in a room

## Content-Only Edits

If a task only changes story, room layout, objective order, enemy count, pickup count, door locks, screen text, quiz options, or visual keys, prefer config edits. Do not change runtime unless the desired behavior cannot be represented by current config.
